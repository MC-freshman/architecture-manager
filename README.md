# 架构管理台

0.4.0 是架构 3.6.0 的接入改造候选版本，发行验收正在进行。每个人使用自己的工作区、配置、软件和 Git 仓，不需要中心服务器，也不共享运行数据。最终发行状态见根仓 `versions/架构3.6.0-执行记录-20260930.md`。

## 打开与首次接入

1. 双击 `release/Architecture-Manager-0.4.0-portable-x64.exe`。普通用户安装包为同目录的 `Architecture-Manager-0.4.0-setup-x64.exe`。
2. 点“选择工作区”，选择自己的架构目录，例如 `E:\ai`。以后会记住最近目录；也可随时切换。全新用户可从首次页面克隆架构仓，GitHub 登录在系统自己的界面完成。
3. 进入“平台与接入”，在顶部“平台接入向导”选已有平台修复，或填写新平台 ID 并确认创建目录。
4. 在“完整配置”选择准备环境的 Python；在“准备环境”点击检测解释器与 WSL，选择已经就绪的隔离环境。当前已发布隔离控制器需要 Python 3.10 的 Linux 环境；准备用 Windows Python 需要 3.10 或更新版本。缺系统组件时先按提示完成安装/重启，然后继续。
5. 展开软件位置表单，选择所需软件的实际程序文件。版本和本体哈希必须符合已冻结配方；例如 dirsearch 的 PPython 别名指向快照使用的 Python。缺失或不匹配会停在具体步骤，不会靠勾选“支持”消除缺口。
6. 如果工作区还没有 Git 提交身份，在“登记与恢复”填写提交姓名和邮箱；它们只用于本机提交，不代替 GitHub 登录。点“预览一键接入／继续”，核对目标、版本和路径，确认执行。管理台连续保存配置、准备独立环境、备份并真实恢复、绑定 provider、实测能力、安装标准 CLI/MCP 入口、运行认证、登记治理文档并提交配置。

接入维护不需要打开 AI 会话，不需要手写 JSON 或使用控制台。系统登录、UAC、许可和重启在对应系统界面完成；接入确认不授予永久管理员权限、外网扫描权限或软件后续业务操作权限。

首次完整矩阵耗时取决于资源数量；本版仍有已登记的重复资源发现开销，性能修复另轮执行。进度显示当前实际步骤，可点击“停止本次操作”。失败会保存恢复点；回到同一工作区和平台，重新预览后继续。仅补 Git 姓名/邮箱可以继续提交步骤，不重复已通过的安装与认证。修改后的配置会使旧证据失效，管理台会明确拒绝覆盖。仅复制文件或握手成功不会显示“接入完成”。

修复已有接入时，“按当前配置重新生成接入”会读取正在使用的环境和 provider 位置；用于升级版本或重新生成配置。普通失败续接会恢复原输入并核对原摘要，发现他人修改时暂停，不能静默覆盖。

## 客户端支持范围

默认安装标准 JSON CLI 客户端，由它通过真实 MCP stdio 连接调用平台探针。CLI 和 MCP 入口也可以在“客户端入口”页面配置并测试；探针回执必须匹配本次随机 challenge、平台、配置和钉版摘要。

这验证的是客户端工具通路。Codex/Qoder/ZCode/WorkBuddy/豆包/DSH 的厂商原生注册另行标记，不能把标准入口通过说成所有原生客户端已配置。没有可验证入口的客户端显示待适配。正常业务的模型输出由业务客户端生成，维护探针不会伪造业务 submit。

MCP 注册配置导出在 `<平台>/bridge/manager-client/mcp-client-registration.json`。可导入兼容客户端；导出文件存在本身不证明原生客户端使用了它。

## 日常管理

- 平台面显示实际使用版本和认证状态。“排除视图”只隐藏本机列表；不删除平台目录。新 ID 可从合法 bridge 自动发现。
- Agent/Skill 可注册、查看全部内容、停用/移除条目、发布新版本或切换默认版。以 current.json 为当前版；冻结版本不覆盖，正在运行的锁不静默换版。技能目录每页 50 条，引用守卫只按现行启用版本判断。
- “治理”查看缺陷与进度；“文档”查看和编辑顶层要求、计划、说明及更新日志。写入前显示计划和基线哈希；敏感顶层文件需要明确确认。
- “软件”先选所属平台。绝对路径来自该平台本体绑定，入口模板另列；“打开位置”打开实际所在目录。“经连接器启动”走平台会话/provider 协议，明确确认后仅本次允许启动，答复如实显示存活、待人工、未安装或拒绝。原始网关的 allowGuiLaunch 不会被永久打开。
- 新软件先安置、备份及恢复验证，再发布冻结的配方文本。现有发布向导只自动冻结便携 CLI 的版本查询；其它操作和原生 MCP 快照需要对应适配和真实验证。VeraCrypt 的版本基线通过不代表卷创建、挂载或卸载已验证。
- 凭据只填写 reference 引用，不放进计划或 Git。Windows provider 从系统凭据管理器读取 `ArchitectureManager/<引用名>`；首次登记真实凭据由用户在系统界面完成。软件列表或接入探针不展示凭据值。
- 一键接入会按显式路径提交配置与治理文本，并回读 Git；凭据、本体、runtime 缓存不入库。仓库页面的独立操作入口仍有旧式输入框兼容问题，本轮未将它们列为已完成；操作内核保留正常推送、分支/标签、备份与 revert，拒绝 add-all 和强推。

## 证据、备份与旧包

每次检查保存到 `<平台>/runtime/manager-check/<时间>/check.json`，conform 和 matrix 报告保存在同目录；latest.json 仅供最近结果展示。“上次检查缓存”显示的是旧时间，点击检查才会重新执行。

接入状态与恢复点在 `<平台>/runtime/maintenance/manager-onboarding/`。科学环境在本平台 runtime，备份和一条恢复命令在 `inbox/backup/<平台>/manager-environments/<安装 ID>/RESTORE.json`。审计与 checkpoint 在本机 `%LOCALAPPDATA%/ArchitectureManager/audit/`。

0.1.x 已按旧包清理表移入垃圾桶；release 中较早的包是历史发行版。不要把旧包和 0.4.0 候选包的行为混在一起验收。若检查错误点名 app.asar 中的 Python 脚本，请关闭旧候选进程并运行已修复的发行包；新版将辅助脚本置于 app.asar.unpacked。

## 开发与验证

沿用 Electron + React + Node IPC 和计划事务内核。所有写入走计划、基线、checkpoint、原子写、回读、审计。已发布三仓字节只读。

```text
npm install
npm test
npm run build:ui
npm start
npm run package:win
node scripts/verify.mjs E:\ai
node scripts/verify-onboarding.mjs <工作区> <平台ID>
```

第二条回读命令针对已完成接入的真实配置、矩阵、客户端回执、备份恢复及 Git，输出 pass/fail digest，不启动业务任务。历史手工备份若没有 RESTORE-VERIFIED.json，会明确失败，需要补齐真实登记恢复证据，不能当作已通过。

解释器和外部程序使用明确路径与参数数组；不拼接 shell 命令。打包必须保留 `asarUnpack: src/runtime/**/*` 和统一 runtimeFile 路径解析，否则外部 Python 无法读取 Electron ASAR 内文件。
